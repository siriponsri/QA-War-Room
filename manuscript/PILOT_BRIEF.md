# CAPA Evidence Review: prospective pilot brief

Status: LOCAL DRAFT / NOT_RUN. No participants contacted, no independent review completed, no institutional approval or exemption declared. This brief supports planning; it does not authorize external contact, data access or a real manufacturing decision.

## Product question

Can an editable evidence-request and provenance report help a manufacturing QA reviewer identify missing or inapplicable support for one explicitly bounded claim? The initial software demonstration uses original fictional nonsterile manufacturing material. It is not a batch disposition, release authorization or approved CAPA closure.

## Proposed five-minute demonstration

1. Open the existing offline browser demo and point out its synthetic-case banner, claim and assessment cutoff.
2. Request the status record and an applicable effectiveness record; explain why closure status alone does not demonstrate sufficiency.
3. Inspect visible batch/scope/date provenance and show an unavailable response or unresolved evidence gap when the selected demo case permits it.
4. Submit a draft decision with citations, inspect terminal debrief and export JSON/Markdown.
5. Show that a simpler or abstaining answer can be preferable to an unsupported positive claim. Keep the full evidence trail challengeable.

The browser has eight demo cases, not the G4/G5 CLI cohort. Do not describe the new G6 archive as a new browser workflow. The CLI engineering reports can be inspected separately after terminal evaluation. No new visual walkthrough is claimed by writing this script.

## Future observation protocol, if authorized

Owner first selects intended jurisdiction, setting, reviewer population and exact case-use rights, then obtains the relevant institutional/organizational determination for the actual study. No consent or approval template in this project substitutes for that determination. Use independently reviewed cases for any task-quality endpoint. Keep product observers and reference reviewers distinct where their roles could bias the endpoint.

Predeclare the task, comparator, case assignment/order, familiarization, timing boundaries, failure treatment, recorded fields and exclusions before enrollment. A possible within-participant comparison should counterbalance order and model participant/case dependence; sample size and appropriate analysis remain unset. Avoid interpreting a convenience demonstration as representative practice.

Potential outcomes are correct identification of a prespecified evidence gap, unsupported positive recommendations, report correction effort, task completion and observed time within a declared workflow. These are proposed measurements, not achieved benefits. Satisfaction alone would not establish learning. Staff-time savings, transfer to unseen cases and delayed learning each require their own corresponding design and evidence.

## Minimal proposed record

Use study-specific pseudonymous participant codes; case/version, condition/order, start/finish definition, outcome/error codes, corrections and missingness. Consent/identity/contact records, if needed, belong in separately authorized systems. Do not place company dossiers, personal identifiers, recordings or reviewer identities into this reproducibility bundle. Retention, access, withdrawal and permitted analysis require a real protocol.

## Entry and stop conditions

Entry requires actual review/adjudication for the intended decision labels, agreed permissions and an approved/appropriately determined protocol for the setting. Stop if the case has unresolved validity, source exposure crosses the intended boundary, participants mistake the tool for authorized closure, or the software loses traceability. Document deviations instead of silently excluding inconvenient outcomes.
